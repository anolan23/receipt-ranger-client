# Frontend migration: Cognito → backend JWT auth

## Context

The Receipt Ranger backend (Flask) no longer uses AWS Cognito. The Cognito user pool has been deleted, so any call to `cognito-idp.us-east-1.amazonaws.com` now fails. The backend has its own `users` table and issues its own JWTs.

**Your job:** remove every use of Cognito from this frontend (Amplify, `amazon-cognito-identity-js`, hosted UI, etc.) and replace it with the HTTP calls below. All other API endpoints are unchanged. They still take `Authorization: Bearer <access_token>`, but the token now comes from the backend, not Cognito.

Local backend base URL: `http://localhost:8080` (production uses the deployed API URL; keep whatever base-URL config already exists).

## Auth endpoints

All bodies are JSON. All endpoints are under `/auth`.

### `POST /auth/register`

Create an account and sign in immediately.

Request:

```json
{ "email": "user@example.com", "password": "at-least-8-chars" }
```

Response `201`:

```json
{
  "user": {
    "id": "<uuid>",
    "email": "user@example.com",
    "created_at": "...",
    "updated_at": "..."
  },
  "access_token": "<jwt>",
  "refresh_token": "<jwt>"
}
```

Errors: `400` invalid email or password shorter than 8 characters, `409` email already registered, `429` rate limited (10 per hour).

### `POST /auth/login`

Request: same body as register.

Response `200`:

```json
{ "access_token": "<jwt>", "refresh_token": "<jwt>" }
```

Errors: `401` wrong email or password (the message is intentionally generic), `429` rate limited (10 per minute).

### `POST /auth/refresh`

Send the **refresh** token as the bearer token: `Authorization: Bearer <refresh_token>`. No body.

Response `200`:

```json
{ "access_token": "<jwt>" }
```

Errors: `401` refresh token missing, invalid or expired. Send the user back to the login screen.

### `GET /auth/me`

Send the access token. Response `200`: `{ "id", "email", "created_at", "updated_at" }`. Use it to load the current user after a page reload.

## Token behavior

- Access token lifetime: **15 minutes**. Refresh token lifetime: **30 days**.
- Send the access token as `Authorization: Bearer <access_token>` on every other API call, exactly as before.
- Do **not** send the refresh token on normal calls. It is rejected there with `401`.
- Any protected endpoint returns `401` for a missing, malformed or expired access token.

## What to build

1. **Remove Cognito.** Delete the SDK, its config (user pool ID, client ID) and any env vars or dependencies tied to it.
2. **Auth service.** One module with `register`, `login`, `refresh`, `logout` and `getCurrentUser`, wrapping the endpoints above.
3. **Token storage.** Store both tokens and load them on app start. Pick the storage the app already uses for the current Cognito session: secure storage on mobile, and memory or `localStorage` on web. Never log tokens.
4. **Request interceptor.** Attach `Authorization: Bearer <access_token>` to every API request.
5. **Refresh on 401.**
   - When a request returns `401`, call `POST /auth/refresh` once, store the new `access_token`, and retry the original request once.
   - If several requests fail at the same time, make **one** refresh call and share the result (do not fire parallel refreshes).
   - If the refresh fails, clear the tokens and navigate to the login screen.
   - Do not apply this to `/auth/login` or `/auth/register`, where a `401` just means wrong credentials.
6. **Logout.** Delete both tokens locally and go to the login screen. There is no server-side logout endpoint.
7. **Screens.** Update the login and sign-up forms to use the new service. Email plus password is all the backend accepts (minimum password length 8).
8. **Not supported yet.** Hide or remove these until the backend adds them: forgot or reset password, email confirmation codes, social login, MFA.

## Error format

Errors from `abort()` calls on the backend return JSON:

```json
{ "title": "Conflict", "detail": "Email already registered", "status": 409 }
```

Show `detail` to the user for `400` and `409`. A `401` from the auth interceptor itself comes back as plain text, so don't rely on it being JSON.

## Gotchas

- The user ID is now a UUID generated by the backend. Existing data tied to old Cognito IDs is not linked to new accounts, so don't expect old receipts to show up for a freshly registered user.
- Email addresses are lowercased by the backend, so compare them case-insensitively.
- CORS is already open on the backend, so no config change is needed there.

## Done when

- No imports or network calls to Cognito or AWS Amplify auth remain (search for `cognito`, `amplify`, `Auth.signIn`, `cognito-idp`).
- Register, login, reload (session restored), a call after 15 minutes (silent refresh) and logout all work against a running backend.
